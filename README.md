# Undercard

**Audit your support-act shortlist against two audiences.**

A headliner's team usually already has a shortlist of possible openers. The hard question is the trade-off: which act reaches the audience the team wants to grow into without clearly losing the headliner's current fans? Undercard asks Qloo to rank the **same** shortlist twice: once for the headliner's audience and once for 1–3 target-audience reference artists. A fixed, public rule then picks which act to review first, and the brief explains what the evidence does and does not show. The team keeps the decision.

Built solo with an AI coding agent for the [Qloo Agentic Hackathon](https://qloo.devpost.com/). Powered by the Qloo Taste AI™ API.

## Try it

**Live app: https://undercard.wangbohan.biz**

Two-minute path:

1. Click the **Phoebe Bridgers → Olivia Rodrigo fans** preset, then **Audit shortlist**. A live run takes about 30–60 seconds; the steps stream as they happen.
2. Read the priority card and the rank table. Each act has one rank per audience (headliner proxy, target proxy), out of the same pool.
3. Click **Veto** under the priority, pick a reason (for example "dates") and confirm. This is an *original-pool rerank*: the ranks keep their original numbers, and Qloo is asked again only to explain the new priority.
4. Click **Edit target references**, add `Billie Eilish`, then **Run new query**. This is a *new query*: vetoes carry over, and the "Latest change" box says what changed and why.
5. Record **Accept** or **No selection**, then **Save brief & copy share link** to get a signed, read-only link.

## What it does

- **Resolves names with Qloo** and stops on ambiguity. You pick the entity you mean, or answer "none of these": an act Qloo does not have is removed from the shortlist rather than guessed.
- **Ranks the same pool on both sides** (`qloo_rank`, two calls). Before any choice, the server checks that every candidate was ranked on both sides, with no out-of-pool ids and no duplicates. If any act is unranked, the result is **partial** and no priority is given. You can remove those acts and run a new query.
- **Picks a priority by a fixed rule** (server code, not the model): the best rank on the act's weaker side, then the best rank sum, then a stable id. Exact ties are flagged instead of hidden.
- **Explains both sides** (`qloo_compare_audiences`: headliner vs priority, references vs priority) as similarity hints, not causes.
- **Writes a brief with a language model** from that evidence. Every claim is labeled Qloo, Rule or General knowledge. The model cannot change the priority, and a mismatch would be shown.
- **Revisits the shortlist.** A veto triggers an original-pool rerank, with the explanation re-queried for the new priority only. Edited references trigger a new query. Changes are labeled, and both "one candidate left" and "everyone vetoed" are handled explicitly.
- **Flags weak evidence.** Degraded or partial Qloo results, harness warnings and rate-limit retries are shown on the page and passed to the brief.
- **Saves and shares** without a database: the run state and shared briefs travel as HMAC-signed tokens, so a modified link is rejected.

## Qloo tools and why

All Qloo access goes through the official [`@qloo/qloo-harness`](https://github.com/qloo/qloo-hackathon-kit) MCP server (`qloo mcp`, long-lived, calls paced and serialized). Undercard does not call the REST API directly.

| Tool | Input | Question it answers here |
|---|---|---|
| `qloo_describe` | each typed name, `type: artist` | Which Qloo entity is this, or is it ambiguous? |
| `qloo_rank` | the shortlist ids as options; signals = headliner (side A) or the references (side B) | Within this pool, how does each act rank for this audience? |
| `qloo_compare_audiences` | group = headliner or references; candidate = the priority | Which audience tags do they share, and which differ? |

Example: one ranking call with the ids shortened. Ranks are positions within this pool only; raw scores from different calls are never compared.

```json
{ "tool": "qloo_rank",
  "args": { "option_type": "artist", "options": ["<Lucy Dacus>", "<Julien Baker>", "<Soccer Mommy>", "<Clairo>", "<Gracie Abrams>"], "signals": ["<Phoebe Bridgers>"] },
  "result (order)": ["Lucy Dacus", "Julien Baker", "Soccer Mommy", "Clairo", "Gracie Abrams"] }
```

## Validation: with vs without Qloo

Undercard was compared against the same model with the same instructions, case text and effective shortlist, but without the Qloo evidence. The test used 5 cases frozen before the first API call: D1 and D2 as development cases, and H1–H3 held out. Each version ran twice per step, and each case included the same follow-up: veto your own first pick, then edit the references. Every output is archived in [`validation/`](validation/). Automated checks cover only rules and sources; whether Qloo helped is the author's own judgement, not user research.

In short, Qloo gave traceable evidence that contradicted the general-knowledge pick in D1 and H2. In H1 the two versions landed in the same exact tie. D2 and H3 got limited help or a disagreement that cannot be settled here. Qloo also could not separate the three reference artists in D2, and could not find 2 of the 8 country acts in H2. See [`validation/README.md`](validation/README.md).

## Known limitations

- Audience affinity is not ticket demand, booking feasibility or personal preference. Ranks are valid only within the pool they were computed for.
- Candidates come from the team. Fees, dates, scale and willingness are not checked.
- The headliner and the target references are proxies for audiences. A shared affinity does not prove new fans will come.
- The rule optimizes the weaker side. It can choose an act that is strong on one side and middling on the other, even when the team cares more about the target side (case H3). The team cannot weight the sides.
- Qloo coverage is limited in this hackathon environment: some artists cannot be found (H2) or ranked (D2, H3). They are flagged, never guessed.
- `qloo_compare_audiences` compares the reference artists as one group, so differences between individual references are not available.
- The live run takes 30–60 seconds. A burst of Qloo calls on a cold cache can hit the 5 requests/second limit; Undercard retries twice and shows that it did.
- Run state is a signed token. Anyone holding a run's state can keep vetoing on it; there are no accounts or session ownership. Vetoes cannot be undone, apart from editing the shortlist and running a new query.
- Testing was done by the author only, with no user research. Demo cases are hypothetical and use public artists; they do not represent the artists' plans or endorsement.

## How it is built

```text
Browser (Next.js page) ──NDJSON stream──▶ /api/audit, /api/veto (route handlers)
                                              │
              server-owned pipeline (lib/audit.ts, lib/replan.ts, lib/selection.ts)
                 │                                        │
   qloo mcp (official harness, stdio, paced)     brief writer (AI SDK, lib/llm.ts)
```

- Next.js 16 (App Router, standalone output) and TypeScript, with Tailwind.
- [`@qloo/qloo-harness`](https://github.com/qloo/qloo-hackathon-kit) 0.1.26 behind a small JSON-RPC stdio client (`lib/qloo-mcp.ts`).
- [AI SDK](https://ai-sdk.dev) structured output through any OpenAI-compatible endpoint. The deployment uses DeepSeek through OpenCode Go.
- No database. `lib/share.ts` signs both run-state and share tokens with HMAC-SHA256, using separate token kinds.
- Deployed as a systemd service on a small VPS behind a Cloudflare Tunnel. The harness needs a long-lived process, so serverless is not supported.

## Run locally

Requirements: Node ≥ 22.19 and pnpm.

```bash
pnpm install
cp .env.example .env.local   # fill in the values below
pnpm dev                     # http://localhost:3000
```

| Variable | Purpose |
|---|---|
| `QLOO_API_KEY`, `QLOO_BASE_URL`, `QLOO_TRUSTED_BASE_URL` | Qloo hackathon key and base URL. The harness requires the custom base URL to be marked as trusted. |
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | Any OpenAI-compatible chat endpoint |
| `SHARE_SECRET` | ≥ 32 random characters, used to sign run state and share links |
| `AUDIT_DAILY_LIMIT` | Optional, default 60 |

Checks:

```bash
pnpm test        # unit and contract tests (scripted harness, no network)
pnpm typecheck && pnpm lint && pnpm build
pnpm t10 [D1 D2]                                       # with/without-Qloo comparison (spends Qloo and model quota)
T10_CASES=scripts/t12-holdout-cases.json pnpm t10      # held-out cases H1–H3
pnpm e2e [baseUrl]                                     # end-to-end against a deployment (spends quota)
```

Container: `docker build -t undercard .` builds a standalone image that includes the harness. `scripts/deploy-racknerd.sh` shows the VPS deployment used here: build the image, copy the standalone output, swap it in, run a health check, and keep the previous build for rollback.
